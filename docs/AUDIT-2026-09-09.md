## 1. P0 · 致命：身份公钥长度契约差一字节

这是「主要功能无法实现」的直接原因。

### 证据链

1. Kotlin 侧 `ShowMyCodeScreen`（`android/app/src/main/java/chat/dc/app/addfriend/AddFriendScreen.kt:174-181`）构造二维码载荷：

   ```kotlin
   AddFriendPayload(
       name = SignalCore.deviceName(context),
       identity = session.identityKey(),   // ← 来自 Rust
       ...
   )
   ```

2. Rust 侧 `SignalSession::identity_key()`（`crates/core/src/ffi.rs:166-169`）返回 `d.identity_key()?.serialize().to_vec()`。

3. libsignal 中 `IdentityKey::serialize()` 即 `PublicKey::serialize()`，实现在
   `third_party/libsignal/rust/core/src/curve.rs:122`：

   ```rust
   let mut result = Vec::with_capacity(1 + value_len);
   result.push(self.key_type().value());      // 1 字节类型前缀
   ... result.extend_from_slice(v)            // 32 字节密钥
   ```

   **即 33 字节，不是 32 字节。** 对应 `PublicKey::try_from(&[u8])`（同文件 193 行）也按 33 字节反序列化。

4. 但 `android/app/src/main/java/chat/dc/app/addfriend/AddFriendPayload.kt:34` 硬断言：

   ```kotlin
   require(identity.size == 32) { "identity must be 32 bytes" }
   ```

### 后果

- **「出示我的码」页面一进入即抛 `IllegalArgumentException`**，加好友主功能 100% 不可用。
- 扫码侧 `ScanToAddScreen` 调用 `sasWith(..., it.identity)` → Rust `IdentityKey::decode(32 字节)` 必然失败 → 安全码永远显示占位「……」，带外比对形同虚设。
- `pin_identity` 同理失效，TOFU 免扫码重连无法建立。

### 为什么既有测试没抓到

- `crates/core/src/handshake.rs` 的测试（如 `sas_matches_and_detects_identity_substitution`）直接传 `IdentityKey` **对象**，从未走「序列化 → 跨 FFI → 反序列化」这条真实路径，字节层契约零覆盖。
- `android/app/src/test/java/chat/dc/app/addfriend/FrameCollectorTest.kt:22,65,80` 用 `random(32)` 构造 identity，**把错误的 32 字节契约固化成了绿色测试**。
- 没有任何 Kotlin 测试覆盖 `ShowMyCodeScreen` 的真实载荷构造。

这正是「测试全绿但功能不可用」的典型成因。

### 修复

- `AddFriendPayload.kt` 断言改为 33 字节，KDoc 注明「含 1 字节曲线类型前缀，与 `SignalSession.identityKey()` / `IdentityKey::decode()` 为同一契约」。
- `FrameCollectorTest.kt` 三处 `random(32)` → `random(33)`（bucket 仍为 32，未动）。
- `crates/core/src/handshake.rs` 新增回归测试锁定该跨语言契约。

## 2. P0 · 主功能为空壳（端到端链路断裂）

| 功能 | 文档/注释暗示 | 实测实现 |
|---|---|---|
| 聊天收发 | 加密聊天 | `ChatScreen.kt:44-57,153-160` 发送仅 `messages.value + Message(...)`，**纯内存、无加密、无传输、不落盘** |
| 消息列表 | 会话列表 | `MessagesScreen.kt:93-101` 恒空态，无数据层 |
| 联系人 | 联系人页 | `ContactsScreen.kt:62` 恒空态，不落库 |
| 节点服务 | 「人人即节点」前台服务 | `NodeService.kt:15` 自述「当前为占位」 |
| P2P 传输 | iroh 打洞/中继 | Rust 侧无 `IrohNode` FFI 导出（全仓 grep 无匹配），Kotlin 侧无调用点 |
| 联系人落库 | 持久化 | Rust 侧无 `ContactStore`（grep 无匹配） |

**即便加好友流程修复后跑通，也没有任何代码把 `SignalSession.encrypt/decrypt` 接到传输层上。**
从「加好友」到「发出第一条消息」之间的链路不存在。

另注：`ShowMyCodeScreen` 从不计算也不展示 SAS，**只有扫码方单侧显示安全码**，文档所称「两端各算一端、肉眼比对」在当前实现下无法完成。

## 4. 环境可复现性问题（本机实测）

按 README 与 ENVIRONMENT.md 的命令逐步复现，全部失败：

| 命令 | 结果 |
|---|---|
| `cargo check --no-default-features` | ✅ 通过（纯逻辑层无 C 依赖） |
| `cargo test --no-default-features` | ❌ `error calling dlltool 'dlltool.exe': program not found` |
| `cargo test --no-run`（全功能） | ❌ 编译通过但**链接失败**：`crt2.o: undefined reference to _gnu_exception_handler`、`DllEntryPoint` |
| `cargo check --all-targets`（全功能） | ❌ `Could not find protoc`（libsignal 的 SparsePostQuantumRatchet 构建脚本要求） |

根因：

- **C1** `protoc` 未安装且不在 PATH。
- **C2** MSYS2 的 `C:/Users/13682/msys64/mingw64/bin`（含 `dlltool.exe`）**不在 PATH**，而 `.cargo/config.toml` 的 `OPENSSL_DIR` 却指向 `C:/Users/13682/msys64/mingw64`。ENVIRONMENT.md 第 8 条与其「构建命令速查」都写了要导出 PATH，但 README 完全没提。
- **C3** `.cargo/config.toml` 指定 `linker = "x86_64-w64-mingw32-gcc"`，与 rustup 自带 self-contained CRT 版本不匹配，链接期缺 `_gnu_exception_handler` / `__mingw_oldexcpt_handler` 等符号。ENVIRONMENT.md 第 13 条称已用此方案解决，实测未解决。
- **C4** `android/app/src/main/jniLibs` 不存在 → 本地无 `libdc_core.so`，即便装上 APK 也无法加载 native 库。

## 8. 遗留与建议（本次未处理，需决策）

> 处置进度见第 9 节；本节保留审计时点的原始清单。

1. **端到端链路缺失**（第 2 节）是架构级缺口，不是小修能解决的，需要专项排期：联系人落库（`ContactStore`）、传输层 FFI（`IrohNode`）、聊天页接加密与队列。
2. **SAS 单侧问题**：出示方目前不计算安全码，带外比对无法闭环。需先确定交互设计（扫码后回传还是出示方后续补算）。
3. **本机构建环境**（第 4 节 C1–C3）：建议把 `protoc` 与 MSYS2 PATH 固化进 CI 之外的本地脚本，并重新评估 `.cargo/config.toml` 的 linker 选型。
4. **`third_party/` 不入库**：CI 每次从网络浅抓取 libsignal 与 iroh，存在供应链与可用性风险（抓取失败即全量构建失败），建议评估 vendor 或制品缓存。
5. **9 个未合入分支**：建议明确取舍（合入或删除），避免继续产生「本地能跑、main 跑不了」的错觉。
